-Goal-
Given a text document and a list of entity types, identify all entities and the relationships between them. Output both using the specified formats. The input may be an email, a structured table, or plain text — adapt accordingly.

---

-Steps-
1. Identify Entities:
1.1. Extract entities of the following types: '[{entity_types}]'
Format: '("entity"{tuple_delimiter}<name>{tuple_delimiter}<type>{tuple_delimiter}<description>)'
  * Email: 'Subject: <subject> | ID: <mail_id> | Date: <YYYY-MM-DD HH:MM> | Tone: <formal/casual/transactional/notification/alert> | Summary: <1-sentence>'
  * Person: 'Account: <email> | Name: <name/None>'
  * Organization: 'OrgName: <organization_name> | Department: <department/None>'
  * Topic: 'Priority: <high/mid/low> | Summary: <Core topic of this email in 1 sentence>'
  * Event: 'EventName: <event_title> | Schedule: <YYYY-MM-DD HH:MM> | Location: <place/None> | Status: <confirmed/tentative>'
  * Attachment: 'Filename: <name> | Type: <file_type> | Summary: <content_summary>'

1.2. Extraction Rules by Entity Type:
* Email Rules:
  - The 'name' (title) of an Email entity MUST always be the <mail_id> (Unique Identifier).
  - CRITICAL: If the 'ID:' field is missing, unreadable, or empty, DO NOT create the Email entity.
  - CRITICAL: NEVER generate or use dummy IDs (e.g., 'MAIL_001', 'mail_001', 'temp_id'). Only authentic IDs from the source data are allowed.
  - The 'Title' attribute MUST use the exact subject from the '[제목]' field. If the subject is missing or empty, set it to '(제목 없음)'.
  - Date Attribute: Use the exact value from the '날짜:' field. Format: YYYY-MM-DD HH:MM (Include up to minutes; exclude seconds). If the date field is missing or unreadable, set it to 'None'.
  - Tone Classification (Select ONLY ONE): formal = Professional business emails, official correspondence from institutions/professors. casual = Informal emails between acquaintances or personal contacts. transactional = Automated transaction emails (payments, refunds, order confirmations). notification = Service alerts, newsletters, marketing updates. alert = Security codes, password resets, urgent warnings.
  - CRITICAL: No values other than the five specified above are allowed. If Tone cannot be clearly determined, select the closest matching value. 'None' is strictly forbidden.
  - Summary MUST be a concise, one-sentence description of the email content.
  - CRITICAL: All Email entity names and all relationship references to Email IDs MUST use the uppercase form of the ID.
* Person Rules:
  - The 'name' (title) of a Person entity MUST always be the Account (email address). Do NOT use the display name as the entity name, even if available.
  - CRITICAL: NEVER include the display name in the entity name field. Display names belong ONLY in the 'Name' attribute of the description.
  - Integrate multiple Person mentions with the same Account into a single entity.
  - The 'Name' attribute should only be filled if a display name is explicitly mentioned. Otherwise, set it to 'None'.
  - CRITICAL: Do NOT create a Person node if the Account (email address) is unknown. Each Person entity MUST have a valid email address as its identifier.
  - CRITICAL: NEVER use or generate fake/dummy email addresses (e.g., '@unknown.com', '@unknown', 'user@example.com') as an Account.
  - If a valid, real-world email address cannot be identified from the text, the Person entity MUST NOT be created.
* Organization Rules:
  - The 'name' (title) of an Organization entity MUST be the OrgName.
  - Extract ONLY organizations, institutions, or companies explicitly mentioned in the text.
  - CRITICAL: Do NOT classify Hotels, Cafes, Buildings, physical locations, or meeting venues as Organization.
  - CRITICAL: Do NOT create or hallucinate organization entities based on inference or context alone if the specific name is not present.
  - The 'Department' attribute should be filled ONLY if explicitly stated; otherwise, set it to 'None'.
  - If multiple departments belong to the same Organization, they should be linked to a single Organization entity.
* Topic Rules:
  - Extract ONLY contextual themes that represent the core purpose of the email (e.g., 'Claude Pro Refund Processing', 'Web Tutoring Schedule Coordination').
  - The 'name' (title) MUST be a concise and reusable noun phrase summarizing the theme — prefer stable/generalizable names, avoid exact dates/identifiers/long phrases.
  - Do NOT extract as Topics: technical terms, file names, coding stacks (Python, Flask, CSS); one-time codes, alerts, or emails lacking substantive discussion; pure system notifications, OTP messages, or security alerts without meaningful context.
  - Consolidate multiple mentions of the same context into a single, normalized Topic entity. For recurring automated emails (e.g., OTP), use a single generalized Topic such as '인증코드 수신' rather than one Topic per email.
  - Priority Classification: high = requires immediate response/action (deadlines, urgent requests, payment errors). mid = general information exchange or ongoing discussions. low = simple notifications, newsletters, automated system emails.
  - CRITICAL: Do NOT create a Topic entity if there is no clearly discussed subject. Use the body text as the primary source; the subject line may support only when the body is too short/minimal.
* Event Rules:
  - The 'name' (title) of an Event entity MUST be the EventName.
  - Extract ONLY if explicit date or time information is present in the text.
  - CRITICAL: Do NOT create an Event entity if the 'Schedule' attribute cannot be populated.
  - Do NOT extract class titles, content names, or session titles as Events unless accompanied by specific scheduling information.
  - If 'Status' cannot be clearly determined, mark it as 'tentative'.
* Attachment Rules:
  - The Attachment entity's Summary must be based on the provided summary text and strictly follow the defined format.
  - See integrated_document_rules for how Attachment extraction interacts with the '[첨부파일 요약]' section.

1.3. Extraction Rules for Integrated Documents:
  * MAIN CONTENT: Extract Email, Person, Organization, Topic, and Event entities from the main email header and body.
  * If the text contains a section marked "[첨부파일 요약]", apply the following rules EXCLUSIVELY:
    - Extract ONLY 'Attachment' type entities from this section.
    - CRITICAL: Names, email addresses, organizations, topics, dates, and labels appearing inside this section are attachment content only and MUST NOT be extracted as separate entities.
    - CRITICAL: DO NOT extract any Person, Topic, Organization, or Event entities from content inside this section, even if they appear meaningful.
    - CRITICAL: Violating this rule is an extraction failure.

2. Identify Relationships:
  * Relationship directions are fixed — do NOT reverse them. Source and Target MUST match the specified entity types exactly.
  * Format: '("relationship"{tuple_delimiter}<source>{tuple_delimiter}<target>{tuple_delimiter}<type>{tuple_delimiter}<description_in_Korean>{tuple_delimiter}<strength_1_10>)'

  | Type | Source | Target | When to use |
  |------|--------|--------|-------------|
  | sent_by | Email | Person | Email sender |
  | sent_to | Email | Person | Email recipient (To Field) |
  | cc_to | Email | Person | CC recipient (CC field) |
  | affiliated_with | Person | Organization | Person's affiliated organization |
  | discusses | Email | Topic | Contextual topic discussed in email body |
  | schedules | Email | Event | Event/Schedule mentioned in email |
  | has_attachment | Email | Attachment | File attached to email |

  Rules:
    * CRITICAL: Each relationship MUST have exactly ONE type from the allowed list. NEVER combine multiple types in a single relationship.
    * Self-mail rule: If the sender and receiver are the same email address, create TWO separate relationships (sent_by and sent_to).
    * affiliated_with target MUST be an Organization type.
    * sent_to MUST be used ONLY for primary recipients (To field). Use cc_to for carbon copy recipients.
    * has_attachment MUST be created ONLY if the attachment is explicitly mentioned in the text.
    * Do NOT use sent_by, sent_to, cc_to if no Email entity exists.
    * Do NOT create relationships that are NOT clearly supported by the text.
    * Relationship weight MUST be a float between 1.0 and 10.0. Explicit: 7.0+ / Inferred: 4.0 or below.
    * Do NOT create duplicate relationships with the same source-target-type combination.
    * Relationship descriptions MUST be in Korean and MUST be a meaningful sentence — NEVER use the relationship type name itself as the description.

3. Grounding Rules:
   * Do NOT extract one-time codes, OTPs, temporary tokens, or any ephemeral numeric/alphanumeric strings as entities.
   * Do NOT extract serial numbers within filenames, or transaction identifiers such as invoice numbers, order numbers, or tracking IDs.
   * CRITICAL: Only extract entities that represent meaningful, persistent concepts, people, organizations, or events.
   * CRITICAL: An entity MUST NOT be created if any of its core fields (name, type, or description) cannot be populated with a valid, meaningful value.
   * CRITICAL: Strings representing absence of value such as 'None', 'NONE', 'null', '없음', '-' MUST NOT be used as entity names under any type.
   * CRITICAL: Do NOT create entities whose name consists solely of a person's display name without a valid email address.
   * Do NOT create duplicate entities.
   * CRITICAL: Every extracted entity MUST be linked to at least one other entity (typically an Email). DO NOT extract isolated entities.
   * Output as a single list delimited by {record_delimiter}.
   * End with {completion_delimiter}.
